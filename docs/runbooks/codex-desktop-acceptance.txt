PLUR — Windows Codex desktop acceptance

Status: not yet performed; tracked in #1625. Do not describe the desktop flow as verified.
For desktop acceptance, install only a candidate built by a run of
windows-editors.yml on main. Pull request runs build the pull request's own
code with its own copy of the workflow and publish an artifact of the same
name, so the artifact name, a green check and candidate-version.txt (written
by the same run) prove nothing about who built it. Before any install:

  gh run view <run-id> --repo plur-ai/plur --json workflowName,event,headBranch,headSha,conclusion

Continue only when ALL of these hold; otherwise stop and do not install:
  - workflowName is "Windows real editors" (the name of windows-editors.yml)
  - event is push or workflow_dispatch (never pull_request or pull_request_target)
  - headBranch is main
  - conclusion is success
  - headSha is the main commit you intend to test

Then download that run's artifact by the head SHA it reported, into an empty
directory:

  gh run download <run-id> --repo plur-ai/plur -n plur-codex-candidate-<headSha> -D <empty-dir>

Never pick the artifact from the Actions list by name. In PowerShell, from
that directory:

  $packages = Get-ChildItem -Filter *.tgz | Where-Object { $_.Name -match '^plur-ai-(core|cli|mcp)-' }
  npm install -g --no-audit --no-fund $packages.FullName
  plur --version
  plur init --codex
  plur doctor --codex

The version must match candidate-version.txt, and its Commit line must equal
the headSha checked above (the file comes from the same run, so it is a
consistency check, not proof of origin). This is a test build, not a
published release. Installing the eventual stable CLI and MCP together, then
rerunning init, returns the registration to the stable installed packages.
A global CLI version alone does not establish which MCP Codex is running.

1. On the existing Windows installation, record Node and Codex versions and the
   current PLUR launch command/pin. Do not include tokens in evidence.
2. Upgrade CLI and MCP together, run plur init --codex, then restart the actual
   Codex desktop app. If its hook review requests trust, inspect and approve
   the PLUR entries through Codex's normal UI.
3. In PowerShell run plur doctor --codex --json. Its target must be Codex, the
   MCP and CLI versions must match, and required token variables must be
   available. This is a terminal check, not desktop acceptance.
4. If using --token-env, ensure the token variable is available to the desktop
   application's launch environment, then fully restart the app. Never paste
   its value into screenshots, reports, model prompts, or this checklist.
5. In the desktop app, open the mapped project. Ask it to save a unique,
   harmless test statement WITHOUT an explicit scope. Inspect the tool result:
   expected remote store/scope and delivery=remote, not delivery=outbox.
6. Start a fresh desktop session in that project and recall that statement.
   Confirm its source is the remote store. Confirm automatic recall also
   reaches the session after hook trust, without manually calling recall.
7. Repeat the default write and fresh-session recall through the Codex CLI in
   PowerShell. Use a second marker so the two paths cannot be confused.
8. If WSL is used, run setup under WSL2 with Linux Node/npm and its own config,
   then repeat in a fresh Codex session. Windows and WSL user homes differ.
9. Verify an off folder still stays silent and an undecided folder still asks;
   neither should silently send a test memory remotely.

Record: OS, Codex desktop version, Codex CLI version, Node version, PLUR runtime
version, project location type (native/WSL Linux/WSL mounted), steps passed or
failed, and sanitized tool-result evidence. Desktop acceptance remains pending
until these checks run in the actual application.
