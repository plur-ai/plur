## Observations (not findings; no modelled property is violated)

1. **`_reconcileQueuedScope` (index.ts ~8920) still uses the old lookup.** It retargets a queued row with `stores.find(url && scope === new && !readonly)`, not `resolveScopeTarget`. An updateEngram that moves a queued row into a conflicted scope therefore retargets it to the first-listed server instead of being refused. The flush's conflict hold keeps the row from being delivered, and the queue invariant still holds (WritePath §2b, any `writable` oracle). So it is a consistency gap, not a leak. Possible fix (source owner): resolve there too, and treat `conflict` like "no writable store" or keep the old target. Not verified: this is from reading the code, not a replay.
2. **The outbox flush's store lookup differs from the resolver for personal scopes.** `routeFor` uses `find(url && scope && !readonly)`, while the resolver gives a personal `user:` scope to the selected (local-first) entry. A row queued before a path store was added for the same `user:` scope is still pushed to the url store. This existed before #1631 and is intentional per the resolver docstring ("the outbox lookups ask 'does any server claim this scope'"). The flush re-runs the leak guard before the push.
3. **Owner question:** a scope claimed by a writable server and by a second, readonly-only server is now a `conflict`, so writes to it are refused. Before, they went to the writable server. No test pins either behaviour. Options: (a) keep it (conservative: any two servers is ambiguous), or (b) count only writable groups toward a conflict.
