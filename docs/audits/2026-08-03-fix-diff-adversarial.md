Run 2026-08-03 with gpt-5.6-sol (codex, read-only) against the ~2,200 unaudited lines written while fixing #794/#811/#813 — PRs #810, #814, #815, #817, #818, #819, #820.

**16 findings: 7 High, 7 Medium, 2 Low. No Critical.**

Verified directly against the code at time of writing: findings 3, 5, 6, 7.

1. **High — stale-lock recovery can delete a new owner’s lock.** [async-lock.ts:273](packages/core/src/store/async-lock.ts:273), [sync.ts:787](packages/core/src/sync.ts:787)  
   Scenario: a crashed process leaves lock token A; contenders B and C both read A. C unlinks A and acquires token C; B then resumes and unlinks the pathname, deleting C’s new lock, before acquiring B. Both enter the critical section and concurrent whole-corpus writes can lose data. This is production-reachable with multiple MCP/CLI processes recovering from one crash. Tests exercise one stealer at a time and never schedule a second acquisition between the comparison and `unlink`.

2. **High — migration planning and schema-version publication are outside the corpus lock.** [runner.ts:145](packages/core/src/migrations/runner.ts:145), [runner.ts:169](packages/core/src/migrations/runner.ts:169), [runner.ts:219](packages/core/src/migrations/runner.ts:219), [runner.ts:263](packages/core/src/migrations/runner.ts:263)  
   Scenario: `runMigrations` and `rollbackMigrations(..., 0)` both read version 2. Rollback removes the v1/v2 fields, then run—planned from v2—applies only v3–v5. Depending on final config-lock ordering, the store reports schema 5 while lacking `commitment`/`content_hash`, or reports schema 0 over a partially upgraded corpus. Production-reachable through concurrent maintenance commands. Migration tests execute run and rollback sequentially; lock tests cover only individual config writes.

3. **High — the pack registry read-modify-write remains completely unlocked.** [packs.ts:205](packages/core/src/packs.ts:205), [packs.ts:213](packages/core/src/packs.ts:213), [packs.ts:532](packages/core/src/packs.ts:532)  
   Scenario: two processes install A and B concurrently. Both read the same registry, add their own entry, and atomically rename complete but different snapshots; last rename wins. Both pack directories remain installed, but one integrity baseline disappears and that pack becomes `unverified`. URL installation performs another unlocked RMW when rewriting `source`. Production-reachable across normal parallel MCP/CLI processes. The “atomic registry” test installs A and B sequentially and proves parseability, not RMW serialization.

4. **High — `recordTensions` still deletes quarantined records.** [index.ts:6232](packages/core/src/index.ts:6232), [index.ts:6282](packages/core/src/index.ts:6282), [tension-store.ts:37](packages/core/src/tension-store.ts:37)  
   Scenario: `tensions.yaml` contains valid records plus one schema-invalid quarantined record. A scan records any new pair; `recordTensions` loads only `.valid` and rewrites the whole file without the quarantined entry, permanently deleting it. Production-reachable through tension-scan persistence. The quarantine regression test covers `confirmTension`/`_mutateTension`, which was updated, but never calls `recordTensions` against the same fixture.

5. **High — the byte-size precheck bypasses the engram-count shrink guard.** [engrams.ts:350](packages/core/src/engrams.ts:350), [engrams.ts:413](packages/core/src/engrams.ts:413)  
   Scenario: a 100-record store contains 11 small records and 89 large ones. An unintended write drops the 11 small records: count falls to 89, beyond the 10% guard, but serialized bytes fall by less than 5%. `mightShrink` returns false, the exact count is skipped, and the data-loss write succeeds. Production-reachable through exported `saveEngrams` and any erroneous whole-corpus caller. Tests use homogeneous generated records and a 50% slice, so record count and byte size move together.

6. **High — the `status()` throw-path fix does not cover the newly strict record stores.** [index.ts:6102](packages/core/src/index.ts:6102), [index.ts:6127](packages/core/src/index.ts:6127), [tools.ts:2406](packages/mcp/src/tools.ts:2406)  
   Scenario: the primary corpus and registry are healthy, but `episodes.yaml` is truncated or `tensions.yaml` has a non-list top level. `status()` now throws before returning diagnostics. MCP `session_start` awaits it unguarded, so the session cannot start; `session_end` and status/doctor surfaces also fail. Production-reachable after corruption or interrupted older writes. The new status test corrupts only `registry.yaml`; record-store tests exercise their loaders and writers directly, not startup/status callers.

7. **High — atomic config replacement broadens permissions on credential-bearing files.** [sync.ts:872](packages/core/src/sync.ts:872), [index.ts:6685](packages/core/src/index.ts:6685), [config.ts:19](packages/core/src/schemas/config.ts:19)  
   Scenario: `config.yaml` was secured as `0600`, contains a remote bearer token or Postgres DSN, and resides under a traversable PLUR directory. `atomicWrite` creates a new inode without preserving the old mode; under umask `022` it becomes `0644` after rename. Store registration, scope-metadata persistence, dismissal writes, or migrations can therefore expose credentials to other local users. Production-reachable on POSIX. Tests validate bytes and atomicity but never `chmod` an existing config and inspect its post-write mode.

8. **Medium — legacy Postgres rows with `search_text IS NULL` are never backfilled.** [storage-postgres.ts:1391](packages/core/src/storage-postgres.ts:1391), [storage-postgres.ts:554](packages/core/src/storage-postgres.ts:554)  
   Scenario: an upgraded database has an active engram and existing embedding from before `search_text` existed. After upgrade, both `search_text` and `content_hash` are NULL. The missing arm is false because the embedding row exists, while the stale arm is false because it requires non-NULL `search_text`; a previously stale vector therefore remains stale indefinitely. Production-reachable on database upgrades. The legacy test NULLs only `content_hash` on a newly written row whose `search_text` is populated.

9. **Medium — staleness hashes a lossy tokenization, not the text actually embedded.** [fts.ts:83](packages/core/src/fts.ts:83), [index.ts:5389](packages/core/src/index.ts:5389)  
   Scenario: a statement changes from “use X” to “do not use X”. `do` is shorter than three characters and `not` is a stop word, so both token sequences and hashes are identical. The vector was computed from raw `engramSearchText`, which did change, but both Postgres and PGLite declare the old vector current and never refresh it. Production-reachable on ordinary meaning-changing edits. Tests use “cats” → “databases”, where retained tokens necessarily change; they contain no stop-word, punctuation, case-only, or short-token collision.

10. **Medium — `sync()` holds the store lock across all remote Git operations.** [index.ts:5661](packages/core/src/index.ts:5661), [sync.ts:651](packages/core/src/sync.ts:651), [sync.ts:677](packages/core/src/sync.ts:677)  
    Scenario: fetch, pull/rebase fallback, and push each approach their 30-second command timeout. All engram writes are blocked throughout; a cross-process asynchronous writer can exhaust its 90-second acquisition timeout and fail. With a Postgres primary, this holds the database advisory lock even though Git is operating on local files. Production-reachable with slow or unavailable remotes. Sync tests use fast local repositories and do not attempt a concurrent write during network delay.

11. **Medium — staged pack installation is atomic to readers but not crash-durable.** [packs.ts:436](packages/core/src/packs.ts:436), [packs.ts:448](packages/core/src/packs.ts:448), [packs.ts:488](packages/core/src/packs.ts:488), [packs.ts:506](packages/core/src/packs.ts:506)  
    Scenario: copied files and generated `SKILL.md` are never fsynced, nor is the staged directory. The pack is renamed live, the old pack is deleted, and the registry is then durably committed. A power loss can therefore leave a durable registry pointing at a missing, truncated, or incomplete pack while the previous version is gone. Production-reachable during installation. Tests simulate ordinary exceptions and inspect post-return state; none exercise power loss or verify fsync ordering for nested pack contents.

12. **Medium — restore loss planning is performed before acquiring the store lock.** [backup.ts:554](packages/core/src/backup.ts:554), [backup.ts:590](packages/core/src/backup.ts:590)  
    Scenario: `planRestore` reads current IDs, then another process learns an engram before restore obtains the lock. Restore copies that newer store aside and replaces the live corpus, but `wouldLose`, `unrecoverable`, warnings, and the returned result omit the new engram. The data is recoverable from the superseded copy, but the operation violates its explicit contract to name what it removes. Production-reachable with concurrent MCP writes during CLI restore. Restore tests are entirely sequential.

15. **Low — drop-log trimming can erase an append that never takes the trim lock.** [drop-log.ts:76](packages/mcp/src/drop-log.ts:76), [drop-log.ts:83](packages/mcp/src/drop-log.ts:83)

16. **Low — `YamlStore.save` gained an unconditional extra full-corpus read and parse.** [yaml-store.ts:28](packages/core/src/store/yaml-store.ts:28), [yaml-store.ts:34](packages/core/src/store/yaml-store.ts:34)
