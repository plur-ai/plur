# 0.24.0 — retrieval and injection overhaul

Every behaviour change a user or an integrator can notice is listed here. The
short form is the `## 0.24.0` section of `CHANGELOG.md`.

## Recall

- **Feedback is part of recall's ranking.** A memory's net rating moves it in
  hybrid recall (the default for `plur recall` and MCP `plur_recall`, in
  process and a store's own searches) and in injection alike: each result gets a rank-based score scaled by its
  feedback factor (up to x1.3 for well-rated, down to x0.5 for badly rated
  memories), and the list is re-sorted. With no ratings the order is unchanged.
  Keyword-only recall (`plur recall --fast`, `plur_recall` with
  `mode: keyword`, the library's `plur.recall()`) and semantic-only recall do
  not apply it yet.
- **Keyword weight is always positive.** A word found in most memories still
  counts a little (`log(1 + (N - df + 0.5)/(df + 0.5))`), so small stores no
  longer come back nearly empty for ordinary words.
- **Fading breaks ties in hybrid recall.** Equal keyword scores share a rank,
  and equally scored results are ordered by faded strength: a memory left unused ranks
  below a fresh one. Locked and pack memories do not fade. Strength is a
  tie-break only; it never outranks a better match.
- **Nearby rules that do not apply are left out of injection.** A memory that
  is nearly the same text as a memory already chosen from the ranking (word
  overlap at least 0.4, words compared by their first five letters; pins are
  not compared) is skipped when the task names a word only the chosen one has
  and no word only the skipped one has. On the labelled INJ-1 tasks this stops
  the not-applicable neighbour on most tasks without losing a needed memory;
  variants the task does not tell apart are all given. Words are runs of ASCII
  letters and digits only, so the rule does not fire on text in non-Latin
  scripts, and it sees an accented word only in its ASCII parts.
- **A corrected memory takes the old one's place in injection.** When the
  ranking injection uses finds a memory that a newer, deliverable one
  replaced, the injected block carries the replacement in its place (and at
  its rank). `plur recall` output does not substitute it.

## Injection

- **Unified injection is the default.** The injected block is recall's ranked
  list behind the pinned slot. `injection.mode: legacy` in `config.yaml`
  brings back the previous selection for this release (rollback path; it is
  the only mode with spreading activation). On a 14,000-memory store copy the
  right memory is injected for about 89 of 100 questions on two test sets
  (0.23: 1 and 15). Related keys: `injection.recall_limit` (default 20),
  `injection.prohibition_ratio` (0.2), `injection.query_min_terms` (4),
  `injection.min_relevance_signal` / `injection.min_relevance` (no cut-off by
  default: no signal met the bar of emptying the task section on unrelated
  prompts while losing at most 1 target in 30. The nearest, `cosine` at
  0.714, empties it on about half of unrelated prompts and loses about 1
  target in 22; set it only if you prefer that trade).
- **Pins once per context (Claude Code).** In the Claude Code hooks pinned
  engrams are injected on the first prompt
  and after a compaction (or resume), not on every skill, agent or plan-mode
  event in the same context. A subagent is its own context: it gets the pins
  once (keyed per subagent id). A delivery is recorded only when the block
  actually held a pinned engram, so a failed or pin-less injection never
  suppresses later ones. The Codex, Cursor and Antigravity hooks send the pins
  with every injection they make.
- **Event hooks use the unified pipeline, keyword-first.** Plan-mode, skill,
  agent and subagent events run the same selection as the first prompt. They
  take the keyword leg unless the embedding model is on disk, the embeddings
  cache is warm and no other hybrid run of the session is live; an event
  never downloads the model, never starts the background cache build and
  never contacts a team server (except in a remote-only folder, which has no
  local store).
- **Event hook timeout 20 s.** `plur init` now registers the event hooks with
  the main hook's 20 s. Installs made before keep 10 s and keep working: an
  event run bounds itself to about 9.5 s in total. `plur doctor` names each
  event hook still registered below 20 s.
- **Vague prompts and event labels get session context** (stored session
  task, project scope label, git branch, last two user turns) added to the
  query.

## Pinning policy

- **`pinning.agents: allow | request | deny`** (default `allow`) decides
  whether an agent may pin. Under `request` an agent's pin is stored unpinned
  as a pin request for the owner (`plur pin review`); under `deny` it is
  refused. Raising a pin's priority or making it a hard-tier pin follows the
  same policy; a pin request cannot carry it, so under `request` it is refused
  too.
- **Registering a new store is owner-only under `request` or `deny`,** because
  a store's pinned engrams load into every session: `plur stores add`,
  `plur remote`, `plur login` (a new server, or a new scope on one),
  `plur scopes register`, `plur stores discover --register`, MCP
  `plur_stores_add` and `plur_scopes_discover` with `register: true`. A token
  piped into `plur stores add --token -` counts as an agent (use
  `--token-env`). Core refuses only additions: re-adding a registered store,
  rotating the token of one, and signing in again to a server for the same
  scopes are not checked against `pinning.agents`, so an agent's re-add of an
  existing store succeeds (`already_registered`). The CLI asks earlier: run
  as the owner, `plur stores add`, `plur login`, `plur remote` and
  `plur scopes register` ask the terminal confirmation on every run, before
  it is known whether anything is added, and refuse without a terminal. A
  token-rotation or re-login script the owner runs non-interactively
  therefore needs a terminal under `request` or `deny`. The one-time move of
  an old `~/.plur/config.json` sign-in at the start of `plur login` (also
  `plur login --status`) registers that server before the confirmation is
  asked; core still refuses it for an agent. Nor are scopes a server newly grants to an entry the
  owner registered: the scope refresh after `plur login` and the MCP
  server's background discovery add them without asking.
- **Pins load where they belong.** A pin with the global scope loads in every
  session. In a session with a scope, a pin loads unconditionally whenever the
  session can see it: a pin within the session's scope, in a personal scope
  (`user:*`, `agent:*`, `local`, or any scope without a shared prefix such as
  `group:`, `project:` or `space:`), or in a team scope mounted under
  `stores:`. A pin in another project or space scope no longer loads. In a
  session with no scope, a scoped pin is a candidate like any other memory and
  is injected only when recall ranks it. This is the unified selection: under
  `injection.mode: legacy` every pin the session can see loads
  unconditionally, with or without a session scope.
- **The CLI is an agent when an agent runs it.** The CLI actor is the agent
  when an agent environment is detected (Claude Code, Codex, the Cursor agent,
  Gemini CLI / Antigravity, opencode) or stdin is not a terminal, unless
  `PLUR_ACTOR=owner` is set. Under `request` / `deny`, these also need a
  confirmation typed at an interactive terminal: `plur pin`,
  `plur pin review approve`, `plur pin apply`, `plur pin priority` when it
  raises a pin, `rescope --apply`, the unlisted `consolidate --apply` and
  `enrich --apply`, `plur import` of pinned records (without it they are
  imported as pin requests under `request` and unpinned under `deny`), an
  undo or a `plur restore --yes` that puts a pin back, and registering a store
  (`plur stores add`, `plur remote`, `plur login`, `plur scopes register`,
  `plur stores discover --register`).
  Scripts that relied on the CLI always being the owner under a restrictive
  policy must now be run from a terminal.
- **What the confirmation stops, and what it does not.** The check is that
  stdin is a terminal. That stops an agent acting through the MCP server or
  through a piped, non-interactive shell tool. It is friction, not a security
  boundary, against an agent that has a shell: a pseudo-terminal (`script`,
  `expect`, a pty library) passes the check, and such an agent can also edit
  `config.yaml` or the engram files directly.

## New commands

- `plur pin` with no id — fit report (priority, tier, cost, overflow), and the
  subcommands `priority`,
  `review approve|reject`, `audit` (asks a model which pins apply to every
  task; writes a proposal into the store root by default, changes nothing),
  `apply <file> --yes` (one journalled change) and `undo <change-id>`.
  `plur pins …` does the same for this release.
- Merging near-copies (`consolidate`) and labelling memories (`enrich`) are
  built and hardened but not listed in the help: in the next release they
  become one `plur review` queue together with contradictions and memories
  held for approval. `plur status` shows the near-copy share meanwhile.
- `plur rescope --plan | --apply <file> --yes | --undo <id>` — proposes a
  scope for global engrams and moves locally owned ones as one undoable
  change.
- Plan and proposal files quote memory text: they are written atomically,
  owner-only (0600) and never through a symlink. `plur forget` and compaction
  redact a removed memory from the change journal only; plan and proposal
  files keep the text they quote, and a memory retired by resolving a tension
  is not redacted.

## Models for the new commands (pin audit, rescope, maintenance)

- **`PLUR_LLM_CMD` bridge.** `--llm-cmd "<command>"` or `PLUR_LLM_CMD` runs a
  host model command with the prompt on stdin and the reply on stdout (for
  example `claude -p --model opus`); `PLUR_LLM_MODEL` names the model recorded
  on results, `PLUR_LLM_TIMEOUT_MS` bounds each call (default 10 minutes).
- **No environment-key fallback for the new commands.** `pin audit` and the
  unlisted maintenance commands never pick up `OPENROUTER_API_KEY` /
  `OPENAI_API_KEY` on their own; with no explicit bridge they refuse.
  `plur tensions --scan` keeps its existing fallback.
- An OpenAI-compatible endpoint is given with `--llm-base-url` (https, or
  plain http to a loopback address only) and `--llm-api-key-env <VAR>`.
  `--llm-api-key <key>` still works but warns: it lands in shell history and
  the process list.

## Learning and search

- **Exact restatements reinforce via MCP.** `plur_learn`, `plur_learn_batch`
  and `plur_session_end` reinforce an existing active engram in the same
  scope when the new statement is equal after normalising case, whitespace
  and punctuation (`decision: REINFORCE` with `existing_id`), instead of
  writing a duplicate. Never similarity-only. `learn.reinforce_exact` in
  `config.yaml` decides when set (the CLI and library default stays off).
- **`structured_data.body` is searchable.** `learn` accepts a validated
  structured body (`--body`, `--kind`, `--outcome` on the CLI) and the body is
  part of the search text. The Postgres tier re-derives its stored search
  text once, in its non-blocking background backfill (`plur reindex-tokens`
  forces it); embedding caches re-embed only the rows whose text changed.

## Speed on large stores

- **Keyword search tokenises each memory once per process** instead of three
  times per query. Same results; on a 14k-memory store a unified injection
  went from about 11 s to under 9 s from the CLI.
- **Binary companion for the embedding cache.** After the JSON cache is read,
  its vectors are also written to `.embeddings-cache.vectors.bin` (exact
  float64 copy). Later processes read that file while the JSON is unchanged
  (same size, modification time and inode) and fall back to the JSON
  otherwise. It is derived, git-ignored and never synced; deleting it is safe.
  It roughly takes the store's vector count × dimension × 8 bytes on disk
  (about 50 MB for 16k memories at 384 dimensions).
- **Hooks keep a finished ranking.** A hook racing its deadline now tells core
  when it needs the answer (`bookkeeping_deadline_at`); the best-effort
  injection counter (a whole-file write on YAML stores) is skipped when less
  than 2 s is left, instead of making the hook throw away a finished result.
  The search itself is not cut short.
- On the 14k-memory store a first-prompt hook in unified mode now finishes in
  about 6 s and an event in about 3–4 s.
- `plur inject --json` reports the unified relevance signals (`relevance`).
- **A late hybrid result is kept.** When a hook's hybrid search misses its
  deadline, it now races the keyword fallback and the hook keeps whichever
  finishes first. Before, a long query could leave an event with nothing:
  the fallback started from scratch and neither finished in time. The racing
  fallback skips its best-effort injection counter, so no store write is cut
  off at exit.
- **`injection_budget` reaches every path.** `plur inject` uses it unless
  `--budget` is given (it was a fixed 2,000); skill, agent and plan-mode
  event hooks use it when it is above their 3,000 floor (it was a fixed
  3,000).
- **Unified task list default raised to 20** (`injection.recall_limit`, was
  10). On the 14k-memory store it lifted the hook path on real-session
  questions from 15 to 17 of 30 at session start and from 13 to 15 on agent
  events, with no empty contexts.

## Configuration robustness

- An invalid value in any of the new keys (`injection.mode`,
  `injection.recall_limit`, `injection.prohibition_ratio`,
  `injection.query_min_terms`, `injection.min_relevance_signal`,
  `injection.min_relevance`, `pinning.agents`, `consolidate.*`,
  `learn.reinforce_exact`) is ignored on its own and the rest of
  `config.yaml`, stores included, still loads. For most keys the default
  applies; an invalid `pinning.agents` becomes `request`, not the `allow`
  default. `plur doctor` names each ignored key.
- This holds for an invalid value inside a block, not for a block of the
  wrong type (`pinning: deny` as a string, `pinning:` left empty,
  `injection: fast`). Such a block makes the whole file fail to load:
  defaults apply and the stores listed in it are not loaded. The pin policy
  stays safe in that case: a `pinning` block that cannot be read is
  `request`.

## Downgrade caveat

- An older release ignores the new `config.yaml` keys. They stay in the file
  (PLUR edits `config.yaml` as YAML and never writes back its parsed form),
  but while the older version runs: `injection.mode: unified` falls back to
  the legacy selection, **`pinning.agents` is not enforced** (agents can pin
  again), and the CLI is the owner as before. Event hooks registered by this
  release still call `plur hook-inject --event …`, which older releases
  handle with their own pipeline.
- Older releases strip unknown keys from the `injection` block when they parse
  it. From this release on, unknown `injection` keys are kept (passed
  through), so keys a later release adds survive a downgrade to this one.
- Pin requests (`structured_data.pin_request`) and journalled changes written
  by this release are inert in older versions: an older release neither
  shows the requests nor can undo the changes. Approve or reject pending
  requests and undo any change you may want undone before downgrading.
